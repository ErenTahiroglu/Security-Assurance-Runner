## Fixed registry and authority

Future owner-approved registry entry is versioned and binds: tool ID/version; official release/source and platform; independently authenticated executable digest or verified release provenance; permitted subcommand and fixed argument array; config/rule digest and version; exact input root and authorized repository/commit; mode/location; output format/version and size; fixed timeout, process/memory/output ceilings; environment allowlist; filesystem read/write scope; network policy; freshness requirement; expected receipts and exit interpretation. Resource values and OS enforcement mechanisms are **UNRESOLVED**, not pretend controls. No user command string, arbitrary executable path, dynamic plugin, implicit installer, shell interpolation or fallback to another tool. A version string, tag or matching untrusted checksum is not authentication.

An independently established project policy authority must approve required categories, config and check inventory. A separately authorized immutable run plan must bind repo ID/full SHA, stage, attempt, mode, expected tool/rules/config and scope. Trusted plan expectation must be external to mutable checkout and its own digest; source-provider identity and executable trust require independent evidence. GOV-01's synthetic key/pin is not that authority. Operator requests and project config cannot create approval; absent policy/plan/identity => REFUSED. No automatic release authorization.

## Execution gates and platform limits

Fixture-only first increment reads inert preconstructed bytes and never invokes binaries. Real process execution is disabled until independent review and owner authorization of concrete isolation plus platform-specific tests: least privilege identity; read-only bounded input view; separate output workspace; argument arrays; sanitized environment; no credentials or inherited provider tokens; network denial; time/memory/process/file/output limits; cancellation and child-tree cleanup; archive/symlink escape defenses; exit and truncation receipts. Sandboxing via directory, subprocess timeout or container alone is not a complete boundary. Linux namespaces/seccomp/cgroups, macOS sandbox facilities and Windows job objects/restricted tokens differ in availability and semantics; do not claim parity. If an OS cannot enforce a required boundary, REFUSE or mark unsupported; do not silently weaken policy.

Update operations, when separately authorized, are isolated from scan runs and disclose endpoint, metadata and data; store source identity, time, hash and rollback/freshness limits. Offline cannot learn unseen revocation or newly published vulnerabilities. A compromised host may forge all local observations. No ECE/ATM authority is delegated: ECE later independently verifies only its accepted evidence capabilities, not scanner quality; ATM is a read-only consumer.
