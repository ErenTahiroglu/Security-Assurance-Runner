# GOV-02 — proposed evidence and coverage contract

**DESIGN ONLY; no parser or real evidence verification implemented.** A scanner result is an untrusted tool claim, not a confirmed exploit or compliance certification. GOV-01's synthetic receipt and digest comparison are not operational provenance.

## Native and normalized records

Proposed bounded versioned run envelope records provider/repo ID, full commit, approved plan digest, run/stage/attempt, declared versus independently verified identities, tool binary/version/provenance, exact allowed mode, config/ruleset identity/digest, scanner start/end/exit/cancel, raw report digest and byte length, native format/version, database source/digest/published/obtained/expiry times and clock/freshness basis, supported and omitted scope, expected/observed checks, errors/skips/unknowns, redaction state and limitations. Preserve raw bytes in restricted storage for later authorized audit; ordinary outputs contain redacted records and raw hash only. Never echo matched credentials, context lines or URL query tokens into ordinary logs, reports, telemetry or error diagnostics; do not follow report URLs or read referenced paths. A digest of restricted raw data can itself enable guessing of low-entropy secrets; protect access to that digest where warranted.

Each normalized finding keeps native tool/rule/finding IDs, native severity and confidence including missing values, optional separately justified normalized severity, path/location (validated relative to scope), native fingerprint and version, evidence reference, redaction version, source state and coverage limitations. Unknown severity remains unknown; no invented confidence. Different fingerprint algorithms/descriptions do not justify merging; retain both until explicit correlation evidence. False-positive dispositions and exceptions require independent scope, reason, reviewer and expiry.

Gitleaks JSON is the proposed fixture candidate; native `Secret`, `Match` and `Line` fields can be sensitive. No actual report or rule is downloaded. Exact v8 JSON structure and behavior require source-version contract review. OSV JSON is a later distinct adapter: preserve ecosystem/package/version, advisory ID, source, DB freshness and unsupported/partial dependency scope. Exit 128 means no packages, not PASS. [OSV output/return codes](https://google.github.io/osv-scanner/output/).

[OASIS SARIF 2.1.0 plus Errata 01](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) is a future common interchange candidate; optional standard fields are not automatically invalid. Per-tool expected fields and producer behavior remain independent requirements. Missing result arrays, empty arrays, absent rules or missing invocation state must be interpreted under the actual producer contract; do not infer completeness from syntax. Unknown schema/version, duplicate security keys, malformed UTF-8, excessive size/depth/strings, truncated data, unsupported location or unsafe URI => explicit error/INDETERMINATE. SARIF and JSON schema validation alone does not authenticate a report.

## State and coverage

Record separately: authorization/preflight REFUSED; execution COMPLETE/INCOMPLETE/FAILED/CANCELLED; report valid/invalid/unknown; observed executable provenance verified/unverified; coverage required/observed/unsupported/skipped; finding severity and disposition; policy PASS/BLOCK/INDETERMINATE; independent external evidence verification; human release authorization. PASS only in a **future** implementation when trusted policy and plan, required adapter execution/provenance, exact rules and applicable coverage, complete report and acceptable findings are established. A valid blocking finding can yield BLOCK even if another required stage is incomplete; untrusted/missing authority cannot fabricate either PASS or BLOCK. Empty findings, exit 0, a matching digest, a green CI run or output claiming success are insufficient. A scanner can miss vulnerabilities even when all checks run.

For each mandatory tool, bind planned versus observed versions, platform, source, inputs, scope, rules, DB freshness and report digest to the authorized run/stage/attempt. Unsupported languages/files, omitted git history, symlink exclusions, skip limits and parser failures remain visible as coverage gaps. An optional successful adapter cannot satisfy a missing required adapter. Detect stale/missing databases and unknown freshness; refuse or INDETERMINATE under policy, never silently use stale data. Determine exact freshness limits through a later owner decision.

Network default: no runtime egress. Gitleaks local dir is the candidate passive mode; restrictions must be tested. Betterleaks has remote sources and active validation/analysis/revocation: all disabled and not authorized. OSV `--offline` and `--offline-vulnerabilities` differ, and DB updates require separately approved access. Semgrep registry/login can enable metrics or remote fetch; pin local config and enforce verified no egress before any use. Scorecard often relies on APIs; defer. Separate approved updates from offline runs; record potential dependency names, paths, filenames and provider-token exposure. These are proposals, not implemented controls.
